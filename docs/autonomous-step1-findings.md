# Deliverable 1 development findings — 2026-10-28

This is a development log for one PEP 703/title example, not the planned 20–50-row
performance evaluation. Prompts were revised using this example, so it must not
later be counted as an untouched test observation.

## Preserved baseline

At this milestone, the original `agent.py`, dependency pins, original tests and
`VERSION` remained identical to `v0.1.0`. During Deliverable 5, only the package
`VERSION` was advanced to `0.2.0-dev`; the baseline implementation stayed frozen. The newer README edit from GitHub was retained. Development
is isolated on `feature/autonomous-search-step1`; no released tag was moved.

Attempt 2 demonstrates an important limitation: finding a quote containing a
value and entity does not establish that the value is the requested metadata.
The public LWN article is commentary about the PEP, not its original publication.
The fix is a stricter source-selection/extraction instruction, not a general proof
that semantic errors are eliminated.

## Final development observation

Attempt 7 generated the query `PEP 703 making the global interpreter lock optional
in python official pep document`, independently selected
`https://github.com/python/peps/blob/main/peps/pep-0703.rst`, and extracted
**Making the Global Interpreter Lock Optional in CPython**. It took **43.036 seconds**,
with **one search call and three application-level model calls**.

The original live result was `INSUFFICIENT_EVIDENCE` because the source identifier
was `PEP: 703`, while the checker expected `PEP 703`. The checker was then fixed to
accept optional colon punctuation between identifier tokens while still rejecting
`PEP 7030`. Replaying the saved live claim against the captured source text passed
and produced `SUPPORTED_CANDIDATE`. This was an offline evidence-check replay, not
a fresh paid end-to-end run after the last fix; the original run record was retained.

A separate HTTP reference lookup **after the autonomous output was saved** confirmed
an exact title match. This lookup was used only to check the development example;
the automatic program neither imports the baseline nor reads the official JSON.
The final successful discovery did not need reformulation; the two-query path was
verified with offline tests, not a successful live two-query extraction.

This validates the initial single-record implementation for discussion, not general
search accuracy. The query itself contains a title-like phrase generated by the
model; pretraining knowledge is a possible influence and is not claimed absent.

## Discussion before Deliverable 2

The automatic path receives no fixed source URL/domain or official JSON answer.
It can choose a poor source or fail to locate a primary publication. Selection is
model judgment, not independently verified authority. Runtime and token usage are
logged, but monetary API-cost evaluation belongs to Deliverable 3.

The next discussion should cover how to distinguish a primary publication from
commentary, how related/mirrored sources should count, and when disagreement should
force manual review. No multi-source comparison has been implemented here.
